# 挑最窄的检查

*[English](check-selection.md)*

挑检查看覆盖，不图方便：改动错了会失败的才跑；改动对错都能过的，一项都不跑。

## 举个例子

你改了 `src/parse.ts` 里的一个函数，往 `tests/parse.test.ts` 添了一个用例。

- 聚焦测试同时覆盖新分支和原有分支。
- 只有别的测试也 import 了这个函数，包级套件才添一份覆盖。搜一遍确认，别假定。
- 只有签名变了，类型检查才添覆盖。只改函数体，它不可能失败。

这一共就一条命令。再跑套件也算不上用功——那是替自己多背一个本不必背的承诺。

## 改动跨界了就放宽

- **共用辅助函数：** 每个调用方都进了范围。跑持有它的那个模块的套件。
- **默认值或配置项：** 你没碰的代码，行为变了。跑它的消费方的套件。
- **序列化、持久化、线路格式：** 旧数据还得能读进来，新数据还得能读出去。两个方向都跑。
- **依赖或构建配置：** 结果看产物，不看源码。构建，然后跑产物。
- **平台相关代码：** 检查得在那个平台上跑。别处跑绿了，不算证据。

## 什么时候放宽到整套

- 改动遍及全仓库：一条 lint 规则、一套测试脚手架、一个共用夹具、一个构建脚本。
- CI 挂了，你在复现它。
- 用户要求的。

## 什么不算证据

- 读一遍代码，然后断定它是对的。
- 测试只断言你刚写完的实现，漏了它承诺的行为。
- 改动前就通过、改动后没重跑的检查。
- 在别的提交、别的分支、别的工作区里跑的检查。
