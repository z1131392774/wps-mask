# 决策记录：一列里不止一种东西，怎么脱敏

Status: implemented — 已被 2026-11-27 的按类型映射记录取代

*[English](2026-11-24-mixed-shape-columns.md)*

2026-11-27 起被取代：[混合列按 JS 类型映射，不按形态](2026-11-27-type-based-mixed-mapping_zh.md)移除了下文描述的形态模式。本文保留，作为形态分类表与它暴露的两个生成器缺陷的记录；其中的形态规则已全部不再适用，手机号模式后来也被整体退役（[决策](2026-11-27-retire-phone-and-simple-header_zh.md)）。

## 问题

真实工作簿里的账号列，常常一行是手机号、一行是邮箱、一行是固话、一行是工号。此前所有模式都先认定"一列只有一种类型"——≥60% 形如手机号就当手机号，≥80% 是数值就当数字，否则当文本。混合列被这轮投票推给文本，于是每个值都变成 `账号4527`：手机号、邮箱、联行号一律拍平成同一个形状。一对一没错、能还原，但作为测试数据毫无用处——这一列原本的任何特征都没了。

强行统一成一种也糟。手机号列里混进 `账号4527`，下游校验直接崩；邮箱位塞一个手机号，换个地方崩。这一列的多样性本身就是要保住的东西。

## 决定

加第五种模式「混合」：形态按**格**判断，不按列。`shapeOf()` 把单个值归为 手机号 / 邮箱 / 固话 / 纯数字 / 字母数字 / 文本，`genMixed` 派给对应的保形生成器：

| 形态 | 留住什么 | 例子 |
|---|---|---|
| 手机号 | 合法性（`1[3-9]` + 9 位）、列内唯一 | `13812345678` → `15924494139` |
| 邮箱 | 域名，只换 `@` 前面 | `li.na@corp.com` → `u005288@corp.com` |
| 固话 | 区号、分隔符、位数、分机号 | `020-88997766` → `020-41283071` |
| 纯数字 | 位数、前导零 | `000123` → `000233` |
| 字母数字 | 字母位与数字位 | `kf_2024_001` → `ud_9309_739` |
| 文本 | 不保，回落 `字段名+数字` | `王小明` → `账号4527` |

一对一不受影响，这正是映射表按**原值**做键、而不是按形态做键的原因：表里存的是 `原值 → 新值`，还原时不必知道这个新值出自哪种生成器。一列混六种形态，照样一键还原。

`guessMode()` 只要发现邮箱或固话，或手机号/纯数字/字母数字/文本这四族里至少出现两族，就回落为 `mixed`；字段名命中手机号、≥60% 形如手机号、≥80% 是数值仍然优先判成手机号或数字。卡片显示模式名和一句按形态的说明；参数快照与编辑逻辑把 `mixed` 和其它模式同等对待。

## 顺手挖出来的缺陷

为了验证混合列写了个探针——同一列连映射两百次。它暴露的 bug 与混合列无关：占用表 `used` 用 `keyOf()` 做键（`n:12`、`s:李雷`、`b:true`），因为"数字 12"和"字符串 12"不能撞；而 `genPhone` 和 `genText` 却拿裸值去查 `used[值]`，永远查不到已占用的槽。于是两个原值可能被分到同一个映射值，表里两条记录指向一个值，还原时谁先命中就是谁。两百次四十值的手机号列里，12 次生成了重复值，11 次把某行还原成了别人的原值——每次映射 6% 概率，不出声，只有对比还原结果才看得见。

两个生成器改成查 `used[keyOf(...)]` 后，同一探针是 0 重复、0 错还原。`engine.test.js` 第 [18] 组把它钉住：只剩 `X99` 一个空位时必须返回 `X99`；第 [16] 组把同一列连做八轮，专门抓这种"偶然才犯"的回归。

同一个探针还揪出纯数字生成器里一句假话：注释写着"0 开头的继续 0 开头"，代码只是把随机区间放宽到含 0——那意味着只有约十分之一的概率刚好撞出 0 开头，两百轮里 184 轮 `000123` 变成了 `216343`。零填充是格式：`000123` 和 `000233` 才像同一列，`216343` 不像。现在生成器原样保留前导零，只随机化它后面的位数；`000000` 退化成留一位在变，`123456` 也不会凭空长出前导零。探针随即归零，第 [20] 组把这条列跑两百次，外加一次端到端的映射与还原。

顺手把 `PURE_DIGITS_RE` 从"三位以上"放宽到"两位以上"：像 `01` 这样的省份/渠道编码原来被判成文本，一映射就成了 `账号6549`。单字符仍然太短、不足以当编码，走文本兜底——这条写进手册，而不是糊过去。

## 考虑过的其他方案

**在面板里让用户逐值选形态。** 否掉了：活儿推回给用户，而需求本来就是"自动处理"。两百个账号要两百次选择。

**取多数形态，接受损失。** 否掉了：产出的数据会在下游校验里失败，而那正是脱敏要避免的事。

**保留域名和本地部分，只遮中间几位（`138****5678`）。** 否掉了：那是展示脱敏，保证完全不同；这里要求值完整、合成、且合法。

**连域名一起换掉。** 否掉了：域名常是公司身份，测试数据里应当还认得出来；换掉之后，任何按域名分组的下游逻辑都失效。代价是域名会留着——写进手册，而不是藏着。

**混合格跳过不脱敏。** 否掉了：在一个"已脱敏"的文件里留着真手机号和真邮箱，是最坏的结果。

**单开一个「账号」模式，用一个生成器搞定。** 否掉了，选了按形态分派：同一个规则不可能既生出合法手机号又生出合法邮箱，而这张分类表正是让行为可解释的东西。

## 后果

形态分类表成了一个契约。加一种形态＝加一个 `shapeOf` 分支、一个生成器、一条断言"什么必须留住"（域名、区号、位数、前导零）的测试。`AGENTS.md` 已把它写成常驻规则。

两条限制只写进手册、没有消除：邮箱域名会留着，`@corp.com` 依然可见；`a1` 这种极短账号的同形态空间很小（`26 × 10`），此时报「空间不足」而不是重复。

判定靠正则，所以数字开头的编码（`2024abc`）、或带 `_ . -` 和空格以外符号的值，会落到文本兜底。它依然一对一、能还原，只是长得不像原值。放宽 `ALNUM_RE` 能救这两类，但会开始吞掉"数字开头的中文"，所以留窄规则、把兜底写进排错表。

README 与 `AGENTS.md` 的预算各调了一次（`1600 → 1780`、`450 → 480`），前提是先删掉了重复表述：第五种模式带五种形态和两条明说的限制，塞不进旧数字里——除非删掉已验证的事实，而那道闸门是为了防臃肿，不是给覆盖面上限。
