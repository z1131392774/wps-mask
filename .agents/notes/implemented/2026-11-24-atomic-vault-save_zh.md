# 决策记录：保存映射表时保留一份校验过的旧表备份

Status: implemented

*[English](2026-11-24-atomic-vault-save.md)*

## 问题

`saveVault()` 先清空隐藏表里的旧密文，再写新分片。两步之间宿主报错或保存中断，表里就没有可读的密文了。而 `loadVault()` 把"密文不存在"读成"这个文档从来没有映射表"，于是失败表现为空映射：表里的假值还在，原值却再也回不来，而且全程没有报错。

同一次读取也把"损坏的表"当成新文档，让篡改和损坏以同样的方式静默。

## 决定

用一列备份把保存做成可回滚，并让读取能区分"新文档"和"读不出的表"：

- 保险箱工作表 A 列是主密文（A1 说明，A2 起分片），B 列是上一份密文（B1 备份标记，B2 起）。
- `saveVault()` 把当前可读的密文（先 A，再 B）复制到 B，读回并核对标记；再把新密文写进 A，整段读回并解密，与要保存的明文比对。任何一步失败都从备份回滚 A（没有旧表就清空），保留可读的备份，并抛出说明三种结局之一的错误。
- `loadVault()`：没有隐藏表 → 新文档、空保险箱。表在但主密文为空 → 报错（`映射表密文为空，为保护数据不返回空映射表…`）。主密文读不出、备份可读 → 用备份恢复并把保险箱标记为 `recovered`，面板据此提示 `映射表损坏，已用备份恢复，请重新保存`。两份都读不出 → 报解密/内容错误。
- `migrateVault()` 只在存储版本低于 2 时改写旧格式桶；当前版本的表原样返回。

## 考虑过的其他方案

**写到第二张临时表再换。** 否掉了：换表本身是一串没有事务的宿主操作，中断后会多留一张可见的工作表。

**把备份放进 `PluginStorage`。** 否掉了：映射属于文档，必须随文档走；插件存储绑定的是安装环境，不是工作簿。

**把读不出的表当成新文档、让用户重新映射。** 否掉了：那正是这次要消灭的静默数据丢失。

**只记录错误，依赖宿主自己的保存。** 否掉了：宿主保存的是工作簿文件，而不是往同一张表的一段单元格里做多步写入的中间状态。

## 后果

隐藏表现在存两份密文，表很大时体积大致翻倍；读回让分片多走一遍。保险箱版本仍是 2，因为这是加法式改动：没有 B 列的表照样能读，下一次保存会补出备份。第 [31]、[32] 组测试覆盖读取分类和备份/读回/回滚路径；面板的恢复提示由第 [20] 组覆盖。

用户面对的从"静默"变成三种明确结果：什么都没写的保存失败、主密文损坏后的自动恢复提示，以及两份都读不出时的显式报错。
