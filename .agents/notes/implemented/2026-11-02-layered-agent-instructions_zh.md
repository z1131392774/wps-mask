# 决策记录：分层组织 agent 指令，决策写进记录

*[English](2026-11-02-layered-agent-instructions.md)*

Status: implemented

## 问题

在本仓库干活的 agent 没有常驻指令，每次会话都从代码里重新推导约定：改动怎么验证、不熟悉的未提交改动怎么处理、设计理由该放哪里。显而易见的解法——根目录放一份大 `AGENTS.md`——会以可预测的方式失败：文件跟着每次事故变长，直到读不动，要紧的规则埋在一堆一年用一次的规则中间。

## 决定

指令分层。根目录的 `AGENTS.md` 只放 agent 每次会话都需要的规则，每条一到三行，并链接到 [`docs/AGENTS.md`](../../../docs/AGENTS.md)（指令文件怎么组织）和 [`docs/development.md`](../../../docs/development.md)（改动怎么做、怎么验证）。只管一个目录的规则，放进那个目录的 `AGENTS.md`。

活过 diff 的结论，写成 `.agents/notes/{proposed,implemented,rejected}/` 下的决策记录，遵循[记录格式](../README.md)。代码和文档描述当前行为；推理与否掉的方案归决策记录。

## 考虑过的替代方案

**根目录一份 `AGENTS.md`，什么都写进去。** 最容易上手，但它没有腾挪的出路：文件一旦超过读者的耐心，剩下的选择只有删掉仍然适用的规则，或者忍受一份没人读完的文件。分层让细节有地方去。

**理由写进 `docs/decisions/`，不分生命周期。** 接近了，但这个文件夹把提案、已落地的决策和否决掉的想法混在一个名字底下。读者分不清一份文档描述的是现实还是废弃的计划；废弃的计划读起来像指令。把状态编进路径，歧义就没了。

**照搬完整的上游体系：记录分类、双语配对、冷冻档案、格式门禁。** 每一部分在它诞生的仓库规模上都值回成本。搬来这里，它们成了没有读者的维护负担，所以推迟到记录树足够大、按类浏览胜过按日期浏览那天。

## 后果

agent 每次会话加载一份短文件，细节只在相关时才加载。代价是纪律：新规则必须放对位置，不能顺手追加；路径搬家时，已落地的记录必须跟着改正。两样都比一份没人信得过的根文件省事。
