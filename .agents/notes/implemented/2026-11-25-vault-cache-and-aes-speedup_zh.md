# 决策记录：用内容戳缓存映射表，并让 AES 变快

Status: implemented

*[English](2026-11-25-vault-cache-and-aes-speedup.md)*

## 问题

面板每个动作都要重读、重解密整张映射表。按这个加载项实际的表规模，这就是主要开销：在本机 MockWPS 上，3 万格的表加载约 2.7 s、保存约 2.2 s，6 万格约 5.7 s 和 6.0 s；纯 JS 密码实现解密一个 1.4 MB 的映射表 JSON 要 3,970 ms。此前的保存每次都会读一遍备份列，还会把刚写进去的密文再解密一次做校验；而一次映射会加载两遍映射表——动作里一遍，随后的刷新里又一遍。

## 决定

**AES 改成标准 T 表实现。** `aes.js` 改用标准的 32 位 T 表（`Te0`–`Te3`、`Td0`–`Td3`），预计算 `SBOX`/`INV_SBOX`，缓存密钥扩展，并为 utf8/base64/CBC 的搬运做块级路径。对外 API（`encrypt`/`decrypt`）、`M1:` 映射表格式、`KEY_TEXT` 和所有错误文案都不变，只有轮函数变快。兼容性由三件事锚定：NIST AES 标准向量；用旧实现解新实现加密的结果、反向也互解；以及与 `node:crypto` 的双向逐字节对拍——一千多组 0 到 200 KB 的随机输入，覆盖中文、emoji 和四字节 UTF-8。在本机 MockWPS 上，1.4 MB 的 JSON 映射表解密从 3,970 ms 降到 98 ms（约 40 倍），加密快 3.2 倍。真机速度未测。

**主列能用就不读备份。** `loadVault` 先解析 A 列，成功即返回；只有 A 解析失败时才去读备份标记和整个备份列。健康的文档上，备份列的取值读取次数为零。A 损坏时仍从 B 恢复，`recovered` 标记与提示都和以前一样。

**保存去掉重复劳动。** `saveVault` 惰性读取旧备份：A 能解析时 A 自己就是备份，只有 A 损坏才读 B；A 能解析时不读 B、直接用 A 重写 B；A 损坏时才读 B，且只有可读备份与 B 现有内容不同才重写 B。之后写 A，校验改成只比较密文字符串——AES 是确定性的，`back === cipher` 就等价于明文相同，再整列解密一遍纯属浪费。这样每次保存少一次全量解密：同一台本机上 3 万格的表现在保存约 152 ms（快 60%）、加载约 96 ms；6 万格保存比旧密码实现快 54%。保存成功后删掉内存 vault 上的 `recovered`，避免缓存的 vault 反复提示"已用备份恢复"。

**给面板缓存一个内容戳。** `Engine.vaultStamp(app)` 从隐藏表算出一个字符串：A1 标记、A 列末行（用 `End` 定位，不整列扫描），以及首、中、末三片各一格，逐段用 FNV-1a 折叠。最多读四个单元格，不整列读，不解密。内容相同戳就相同；`saveVault` 会用随机 IV 重写整列，所以保存后戳必变。`''` 表示没有映射表、空表或读取失败，函数从不抛错——真正读映射表的 `loadVault` 仍是大声报错的路径。面板对 `''` 一律不缓存。

**面板复用已有的东西。** `refresh(useRemember, keepEdits, vaultOverride)` 接受刚加载或刚保存的 vault，`doMask`、`doRevert` 因此只加载一次映射表而不是两次。普通刷新先比内容戳，命中就跳过 `loadVault`：3 万格刷新从 82 ms 降到 42 ms（MockWPS）。`loadVault` 抛错时清掉缓存并把错误抛出去；`doDrop` 重置缓存。功能区的命令不共享面板状态，面板在下一次刷新时通过变化的戳看到它们的写入。

## 考虑过的其他方案

**保留逐字节的 AES 循环。** 否掉了：可读性更好，但在这个加载项实际存储的表规模上慢约 40 倍。T 表是标准且被广泛审查过的取舍，而格式层的兼容性测试让这次改动不会悄悄偏离。

**每次调用都重建 S 盒或扩展密钥。** 否掉了：这是纯开销。表与扩展密钥只取决于 `KEY_TEXT`，每个上下文建一次就够。

**永远读写两列密文，或用再解密一次来校验写入。** 否掉了：整列 COM 读取和第二次全量解密正是这次要省掉的开销。备份只在 A 不可用时才有意义，而确定性的密码实现让密文相等已经足够。

**面板不做内容戳，只在面板动作后重载。** 否掉了：另一个窗口、宏或功能区命令都可能在面板打开时保存映射表。面板拿着过期的副本去映射或还原，会对着错误的记录下手。

**靠整列读取或解密来生成戳。** 否掉了：那正是缓存要避免的工作。因为 IV 随机，一次保存会改变密文的所有字符，采样几个格子足以察觉。

**给映射表文件加版本号或计数器。** 否掉了：为了缓存而改存储格式不划算。从文件字节派生内容戳保住格式，也不需要迁移。

## 后果

缓存是性能手段，不是一致性保证，空档是真实存在的：

- 采样会碰撞。外部编辑只改动 A 列未被采样的行，或只在 A 仍能解析时改 B 列，戳可能不变；后一种情况 `loadVault` 本来也会返回没变的 A，缓存结果与真实加载一致，但任意行编辑时面板可能拿旧 vault 顶着用。
- 读戳和调用 `loadVault` 是两步；两步之间发生外部保存会被当成当前内容（乐观窗口）。
- 多窗口与共享文档的一致性全靠这个戳。功能区的命令不会直接让面板内存失效——下一次刷新才会，而且是通过戳的变化。
- `loadVault` 抛错时必须清缓存，代码确实清了：损坏和解密错误仍然大声报出，不会被旧缓存掩盖。
- 文中两个提速数字是本机 MockWPS 的测量，不是真机测量。四个格子读在真实 COM 宿主上是否比省掉的整列读更便宜、新 AES 在真机上快多少，都还未验证。

验证：本机 MockWPS 上六套测试全绿——engine 429 条断言、taskpane 200 条、AES 新增 42 条——`npm run check` 在 84 个文件上通过。映射表格式规则在 [implementation.md](../../../wps-mask-addon/docs/implementation_zh.md#映射表格式) 中未变；`aes.js` 仍只是混淆而不是凭据，与[产品手册](../../../wps-mask-addon/README_zh.md)的说法一致。
