# 区间不再铺满，置换改成随机成环

*[English](2026-11-24-no-rotation-on-full-interval.md)*

## 问题

用户在看完"数字列是区间内整列错位置换"之后问了一句：这是不是意味着脱敏后的数据还能看出原数据的某些特征？顺带质疑：算不同值个数根本没必要，每次数一下格子就行了。

第一个问题问对了，而且比预想的严重。`assignExact()` 在"不同值个数正好等于区间整数个数"时启用，做法是把原值排序、槽位排序、整体错开 r 位。区间默认就是数据范围，所以铺满时两者是同一组数，结果是**把原列整体旋转**：

```
工号 1~300：假值 = 293,294,…,300,1,2,…,292
排序后与原列完全相同      → 多重集、频次一个不差
位次差全为 292           → 只是一个单参数的替换密码
知道任何一行的真实工号   → 300 行全部反推正确
```

年龄 20~40 各出现一次同理（偏移 6）。顺序编号、窄区间整数列（年龄、评分、1~N 工号）都会落到这条路上。

第二个问题（只数格子）在数字模式不成立：这里的容量单位是"区间里有多少个整数"，一对一要求不同原值占不同槽位。用格数当上界数学上安全，但会把区间撑坏——年龄 20~40 共 44 格，按格数要 44 个槽，区间变成 20~63，映射出 57 岁。文本模式能只按格数，是因为它的容量是 10^位数，格数本身就是安全上界。这次把这条不对称写进了决策记录，也写进了文档。

## 决定

两处一起改，缺一不可：

1. **默认区间留出空槽。** `defaultCfg` 的数字分支不再"刚好够用"，而是 `want = max(need + 1, ceil(need × 1.1))`，区间不够就扩上界：年龄 20~40 → 20~43（24 槽用 21），工号 1~300 → 1~330。至少 +1 保证"不同值个数 < 整数个数"恒成立，铺满这条路径在自动映射下不再出现。10% 与文本后缀位数用同一把尺子。
2. **置换改成随机成环。** `assignExact` 用 `sattolo()` 洗牌槽位再对号入座：结果是单一循环置换，长度 ≥ 2 时天然没有不动点，也不留固定偏移。手改窄区间把区间压到刚好够用时，走的就是这条路。

区间是 `sigOf()` 的一部分，扩了等于换签名——上一轮做的"并集 + `absorbBucket()`"正好接住：老记录搬过去、老假值仍有效、新值从更宽的空间里取。所以这次不需要额外的迁移路径。

## 考虑过的其他方案

**只留空槽，置换不动。** 不够：用户在面板里把区间改窄到刚好够用时仍会退化成旋转，而"刚好装满"在面板里是个很容易出现的状态。

**只改置换，区间不留空槽。** 不够：排序后的多重集仍与原列相同，频次画像照样泄露（虽然不再是单参数可反推）。

**按格数定区间（用户提的"数格子"）。** 否掉了：年龄 44 格要 44 个槽 → 20~63 → 57 岁，区间被撑坏，得不偿失。数字模式必须知道不同值个数，那是容量约束本身，不是可省的统计。

**下界也一起留余量。** 没做：金额往下留会把假值变成负数，年龄往下留会出现 2 岁，是否合理得看字段语义，硬做会把可信度换掉。残留记在文档里：区间的最小/最大值仍等于数据范围，可被观察。

## 后果

`engine.js` 新增 `sattolo()`；`defaultCfg` 的数字分支改用 `want`；`assignExact` 换掉整体偏移。区间比数据宽约 10%（年龄 20~43、编号 1~330），看起来更散，但仍在同一量级，不影响"像真数据"的判断。

老文档里已经映射过的区域不变——那部分历史泄露追不回来，改动只对之后的新值生效；已存设置里的区间会在下次 hydrate 时按并集与空槽规则重新计算，记录随桶一起搬。

测试：第 [16] 组改成手动收窄区间，强制走置换路径，断言"位次差不恒定"（原来只断言无不动点，那对旋转也成立）；第 [26] 组用 300 个编号跑默认路径，断言区间 1~330、假值两两不同、无不动点、排序后与原列不同、位次差不恒定；[24]、[25] 的期望区间跟着变成 43 / 49 / 112。README 的加密边界一节加了"假值还能看出什么"，把残留（min/max、行数、空值位置、行顺序、文本形态）明写出来。
