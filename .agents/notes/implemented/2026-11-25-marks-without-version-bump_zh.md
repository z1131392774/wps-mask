# 决策记录：marks 字段不需要升映射表版本

Status: implemented

*[English](2026-11-25-marks-without-version-bump.md)*

## 问题

标记边框把加边框前的边样式存进映射表，等于给加密 JSON 加了一个 `marks` 字段。映射表格式规则要求：改格式就要在同一改动里加版本字段和迁移，否则要写一条记录说明为什么留成孤儿无妨。旧文档没有 `marks`，如果读取方要求它存在，就会把旧文档当成损坏。

## 决定

`marks` 是可选的新增数据，映射表保持版本 2：

- `loadVault()` 把缺失的 `ranges` 或 `marks` 补成 `[]`；标记边框出现之前写出的文档按"从没画过"加载，这正是事实。
- 没有任何已有键改变含义，也没有桶键改变，所以没有东西可迁移。旧文档的唯一影响是：它已经映射过的区域暂时没有外框，直到再次映射。
- 新保存一律写入 `marks`，这个字段会在加载项第一次保存映射表时出现。
- 混合边规则和字段放在一起：`readEdge()` 在线型、粗细或颜色缺失时返回 `null`，因为宿主无法为一条各格样式不一致的边表达唯一样式。`null` 边是未知样式——从不画，也只清仍是标记样式的格子。
- `marks` 与映射、区域记录在同一次保存里落盘；`prepareMask` 在那次保存前画框并记录，保存失败时 `abortMask` 把边框恢复到映射前。`writeMask` 通过 `restoreMaskBase()` 把单元格、区域记录与 `marks` 一起回滚。
- 颜色是打包整数 `15547004`（R124 G58 B237，`#7C3AED`），不是十六进制字面量：宿主按 RGB 字节序读 `Border.Color`，十六进制值在真机上实测偏红。

## 考虑过的其他方案

**把 `VAULT_VERSION` 升到 3，迁移时补 `marks: []`。** 否掉了：没有数据要转换，只是一个缺失的可选字段；升版会逼所有读取方处理新版本，而这个字段的默认值本来就正确。版本 2 是为真正的 v1→v2 桶改名而存在的。

**把边样式存在映射表之外**（另一张隐藏表或单独文件）。否掉了：没有受治理的格式归属，`dropVault()` 时不会随表清理，映射表的保存/备份保证也覆盖不到它。

**旧映射表加载时直接重画外框。** 否掉了：需要在打开文档时操作宿主，而且只能给从未记录过的样式猜一个值，等于盖掉用户边框。

## 后果

`loadVault()` 给该字段补默认值，`tryParseVault()` 不会因为它缺失而拒绝；但映射表一旦存在，主密文为空仍会被拒绝。测试第 [31] 组钉住"新文档"与"损坏"的区分，第 [45]、[51]–[53] 组覆盖画框、过期记录清理与删除。以后 `marks` 再变，仍然按映射表规则走：同一改动里升版并迁移，或者再写一条这样的记录。
