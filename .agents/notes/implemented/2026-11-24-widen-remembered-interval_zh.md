# 记忆的数值区间只扩不缩

*[English](2026-11-24-widen-remembered-interval.md)*

## 问题

用户在自动映射时撞上一个弹窗：「A 列（年龄）的区间只有 21 个整数，装不下 27 个不同值，请放宽区间或设为「不处理」」，并追问两句：自动映射为什么会遇到这个，为什么还在算不同值。

复现出来的是两个机制叠在一起：

- 快速映射走 `hydrate()`：先按当前数据算一份默认配置，再用映射表里记住的配置整体覆盖它，`min`/`max` 也在覆盖范围内。于是第二次映射用的还是**上一次那批数据的范围**。
- 上一批 20~40 是 21 个整数，正好用满 21 个槽（`defaultCfg` 撑区间时是 `hi = ceil(lo) + need - 1`，cap 恰好等于 need，零余量）。同一工作簿里另一个 sheet 的「年龄」是 20~46，27 个不同值，比旧区间多一格就装不下。

实测（列名「年龄」）：第一批 20~40 记住 20/40；第二批 20~46 仍取 20~40 → 报错；清空记忆后同一批数据区间变 20~46 → 通过。

同一个工作簿里另一个 sheet 同名列值域更宽、或者给表补了行，都会触发。文本模式同理：记住的 `digits` 太小就报「N 位后缀只有 X 个可用」。

至于"还在算不同值"：数字模式的假值不是随机造的，是在区间里做整列错位置换——区间里的整数就是槽位，一对一要求不同原值落在不同槽位，所以「槽位数 ≥ 不同值个数」是硬约束，这个计数既用来撑区间，也用来判断可行性。上一篇里"不用算不同值"的决定只针对**文本/混合的后缀位数**：那里拿非空单元格数当上界就够（不同值 ≤ 单元格数）。数字模式的容量就是区间长度，不算就算不了。

## 决定

记住的设置里，`mode`/`dist`/`dec`/前缀/位数是用户的选择，原样沿用；`min`/`max` 只是"上次那批数据长什么样"，改成**取并集**：

```
cfg.min = min(记住的 min, 本批默认 min)
cfg.max = max(记住的 max, 本批默认 max)
```

只扩不缩。本批数据一定落在本批默认区间内，并集只大不小，所以容量必然够——「装不下」这条在自动路径上不再可能出现。数据变窄时区间也不回收：回收等于换一套映射空间。

区间是 `sigOf()` 的一部分，扩了就等于换桶。所以 `hydrate()` 在扩区间之后立刻 `absorbBucket(vault.maps, 旧签名, 新签名)`，把记录按原键搬过去，并把扩过的配置写回 `vault.settings`。不搬会重演删 `lang` 那次的事故：同一批人在新旧区域各拿一套假值。

搬记录时沿用既有的防重规则（两条：目标桶已有同名键、或这个假值已被占用——就丢这一条），与删 `lang` 的桶名迁移共用同一个 `absorbBucket()`。丢记录不影响反映射，反查走的是全局索引。

只在 `dec <= 0` 且两边都是数字模式时扩区间：小数区间没有容量约束，动了只会平白改签名。

## 考虑过的其他方案

**报错时自动放宽到"刚好够"。** 否掉了：能解决这一批，下一批多一个值又撞线，而且放宽后签名变化没处理，跨 sheet 的假值会分裂。

**记忆只记策略，区间每次按当前数据重算。** 否掉了：改动最小，但同一个原值在不同批次会拿到不同假值，破坏"两个 sheet 里相同数据映射到同一个值"。

**只改报错文案，让人去面板里放宽。** 否掉了：自动映射的价值就是不用开面板；一个纯数据驱动的量不该要求人手工维护。

**区间额外留 10% 余量（像文本后缀那样）。** 没做：文本留余量是为了让随机重试躲开原值，数字模式有整列错位置换兜底；区间一旦有余量，`assignExact` 的全等条件不成立，反而退回逐个随机。

## 后果

`engine.js` 新增 `absorbBucket()`（`migrateVault` 改为复用它）、`widenInterval()`、`copyCfg()`；`mergeCfg()` 改为接收已算好的 `base`，避免每列算两遍默认配置。`capacityHint()` 的报错保留——手改窄区间时它仍然是对的，README 的排错表也按"只有手改才会出现"改了说法。

面板这条链修了两处，都是同一个病因在别处的复现：

1. `doMask()` 会重新 `loadVault()` 再套面板上的配置。扩过区间的 cfg 配上还没搬桶的映射表，等于拿着新签名去空桶里发假值——同一个 28 在另一个 sheet 会变成另一个数。现在它在套面板配置之前也走一遍 `hydrate()`。
2. `refresh(true, true)` 的快照按字段名把**上一个选区**每列的 cfg 整体搬过来，而 `hydrate()` 的并集紧接着就被它覆盖：换 sheet 时旧的窄区间又回来了。快照改为只带回用户真正动过的列（`state.edited`，在 `readCard` 和类型下拉里置位），`keepEdits` 为假时清空。用户没动过的列必须拿 `hydrate()` 算出来的新配置。

`engine.test.js` 第 [24] 组用同一工作簿的三个 sheet 钉住这条规则：20~40 先映射（记住 20/40）；20~46 第二批不再中断且区间变成 20~46；28 在两个 sheet 拿到同一个假值；旧桶并到新签名后只剩一个；更窄的第三批不缩区间、不再新建记录、28 仍是同一个假值；最后旧区域照样能还原成 28。`taskpane.test.js` 第 [12] 组走面板按钮复现同一个场景，卡住面板那一侧的回归。

上一篇记录末尾写着"数字列的映射区间仍然按不同值精确配平，这次没动，要改得单独算一次"。这次动的是**记忆与区间的关系**，配平本身（`hi = ceil(lo) + need - 1`）没有改，只是它现在只在首次识别时决定起点。
