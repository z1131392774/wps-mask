# 决策记录：清除脱敏记录移到功能区

Status: implemented

*[English](2026-11-28-clear-records-in-ribbon.md)*

## 问题

用表格的人是表格用户，不是实现者：「映射表」是我们对那张存放加密记录的隐藏工作表的叫法，用户想清掉本文档的脱敏数据时，没有任何理由把这个词和面板底部的链接联系起来。那个入口——“清除本文档映射表”——藏在面板最底下，不容易发现；每次改面板布局又都得把它保护起来：一个破坏性动作放在可滚动的页脚里，永远在和面板要展示的内容抢位置。

## 决定

删除记录改成功能区动作，并给它单独一个分组：

- 「数据脱敏」选项卡新增「脱敏记录」分组，里面一个大按钮「清除脱敏记录」（`btnMaskClearRecords`，`images/clear.png`），和映射、边框两组并列。面板不再提供删除入口：页脚链接删掉，使用说明改为指向功能区分组。
- 点击后按这个顺序执行：先做只读预检（只读文档里删除会被静默丢掉，所以先拒绝），再弹确认框 `清除后，本文档中已脱敏的数据将无法还原。确定清除脱敏记录？`，然后删表并恢复标记边框。确认框不可用或抛异常都按“不清除”处理：对话框失败绝不删。
- 所有用户可见的句子——保存、读取、损坏、回滚、清除——统一用「脱敏记录」。隐藏工作表名仍是「脱敏映射表」：现有文档靠这个名字认表，改了名旧文档会被当成没有记录的新文档。内部名称（`VAULT_SHEET`、`dropVault`）也不变。
- 结果必须说清楚：没有记录时 `本文档没有脱敏记录。`；成功 toast `脱敏记录已清除。`，恢复过边框就追加 `已恢复 N 块区域的边框。`，再追加 `记得保存文档。`；部分善后失败 `脱敏记录已清除，但有些善后没做完：…。`；删除失败 `清除脱敏记录失败：…`，并把工作表重新隐藏，不假装删掉了。
- 清除不是撤销：它删掉的是还原能力。已脱敏的单元格保留假值，不会写回任何原值；唯一找回的办法是文档的已保存副本。

## 考虑过的其他方案

**保留面板入口，只改个名。** 否掉了：它仍然埋在底部，仍然和面板布局抢位置；破坏性动作需要用户不滚动就能找到的落点，当初难发现正是因为这个。

**叫「清除还原备份」。** 否掉了：“备份”会让人以为别处还有一份拷贝，而且说的是存储而不是后果，听起来比实际操作安全。

**两处都保留，面板和功能区各一个。** 否掉了：一条不可逆的删除路径变成两条，就要维护两套确认与提示、两处入口；一个显眼的落点更简单也更安全。

**连隐藏工作表一起改名。** 否掉了：现有工作簿靠名字认自己的记录表，换名字会让旧文档的记录全部找不到，所有还原都丢失。

## 后果

入口更显眼，措辞用表格用户听得懂的说法讲清后果。旧文档零影响：工作表名、密文格式和内部 API 都不变，不涉及迁移，改的只是文案。确认框和只读预检成了安全网，两者拒绝时记录都保持完整。功能区测试新增一个直测（[16]）：确认→删表→恢复边框→toast，外加取消、只读拒绝、无记录提示、部分善后失败、删除失败但保留表并如实报错；面板测试（[7]）钉住“面板不再有删除入口”。真机未验证：第三个功能区分组在窄窗口下是否放得下；按钮本身无法从外部点击（见[验证页](../../../wps-mask-addon/docs/verification_zh.md)）。
