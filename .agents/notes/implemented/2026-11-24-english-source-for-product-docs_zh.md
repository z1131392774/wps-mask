# 决策记录：产品手册以英文为源稿

Status: implemented

*[English](2026-11-24-english-source-for-product-docs.md)*

## 问题

本仓库里每份手写文档都是英文源稿配一份中文孪生，门禁盯着这个配对。产品手册却是反过来的：为 WPS 的中文用户用中文写成，没有英文版。于是把标准套上来时，`wps-mask-addon/README.md` 一份文件就得做个选择——译成英文保住配对，还是把它豁免掉。手册恰恰是用户会读的那一份，这里答错，等于给其余所有文件立了个坏样子。

## 决定

手册同样以英文为源稿。`wps-mask-addon/README.md` 放英文，`README_zh.md` 放中文，配对遵守与其它文件一样的链接、预算、时效规则。不豁免任何文件：`excludePairs` 保持为空。

## 考虑过的其他方案

**用 `excludePairs` 把手册豁免掉。** 否掉了：标准把豁免留给生成的文件。一份手写文档留着孪生却不守配对规则，正是这条规则要防的漂移；豁免还会一并取消它的链接与锚点检查。

**改成中文为源稿，英文副本用 `_en.md` 后缀。** 否掉了：门禁、它的 slug 函数、以及树里每份文档，都认定 `_zh.md` 是译文的名字。为一个目录反转方向，要改门禁和每一条入链，换来的东西翻译本来就有。

**只留一种语言，删掉双语规则。** 否掉了：那是全仓库范围的改动——删孪生、删配对检查、删写作规则——为了一个文件不值当。

## 后果

中文手册从此是译文，英文一改就得跟着刷新；英文那一半提交得更晚时，门禁会报出来。反向的情况它抓不住：只改中文会通过，因为它只比较两半谁最后被改动。所以中文措辞的改动要么同一次带上对应的英文改动，要么这对文件就悄悄有了同一个事实的两种说法。
