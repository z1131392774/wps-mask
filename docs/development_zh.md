# 开发指南

*[English](development.md)*

这份文档讲两件事：在本仓库怎么完成一次改动，怎么判断改动做完了。指令标准见 [AGENTS.md](AGENTS.md)；agent 每次会话都要读的常驻规则，在[根目录 AGENTS.md](../AGENTS.md)。

## 改动纪律

1. **先读懂，再动手。** 读目标文件、它的测试，再读一份同模式的邻近例子。改动跨过包或模块的边界，边界的定义也要读。
2. **计划落在纸面上。** 三条：改什么、可能弄坏什么、怎么验证。计划凑出第四条，这次改动就大到一次做不完。
3. **改动面越小越好。** 能改现有函数，就不平行加一个；能扩展现有配置对象，就不新增配置文件；能加一条测试，就不重写整套。
4. **边改边删。** 改动让代码、配置或文档过时了，在同一次改动里删掉，并修好指向它的引用。留到「以后再说」，会让正常工作的系统背上维护负担。
5. **没有理由就不加依赖。** 理由要看它省下的代码和维护量，不能只图一时方便。
6. **提交要读得懂。** 一次提交一个逻辑改动，提交信息写清为什么。格式化噪音不和行为改动混在一起。

## 失败与错误处理

- **在入口校验。** 数据从用户、文件、网络调用、进程或模型进入时，在入口处校验并拒绝非法输入。类型化的同进程边界内，相信类型，不做防御性重复校验。
- **结果不明就停下汇报。** 写失败、超时、批量做了一半：说清已知什么、不知道什么、要用户定什么。绝不破坏性重试，绝不假装成功。
- **保留原始错误。** 包装错误以补充上下文时，保留原始消息和堆栈。日志只在处理错误的地方打一次，不要每层都打。
- **明确记录被忽略的错误。** 空的 `catch` 里写一条注释，说明预期的是哪个错误、为什么继续执行是安全的。

## 验证阶梯

先运行能发现本次改动问题且成本最低的检查，改动范围扩大时再增加检查。

1. **针对性测试**，对准改动的函数或文件。
2. **包或模块的整套测试**，改了共享辅助函数或公开行为时跑。
3. **文档门禁**，改了 Markdown、`scripts/check-docs.mjs` 或 `scripts/doc-budgets.json` 时跑：`npm run check`。本仓库没有 linter 和类型检查，不要凭空造一项。
4. **全套测试**，只有全仓库范围的改动、排查 CI，或用户要求时才跑。完整覆盖由 CI 负责；本地重复运行已通过的全套测试只消耗时间，不增加证据。
5. **构建产物或手动跑一次**，改动影响用户实际执行的产物时运行。

如实报告运行了什么命令、返回了什么结果。「应该能过」不算结果。某项检查在当前环境无法运行时，说明是哪一项、什么原因，不要直接跳过。

## 审查清单

交出去之前，先读自己的 diff，逐条回答。

- 这次改动只做一件事吗？描述说清做了什么、为什么了吗？
- 每个改动的文件都有理由吗？有没有格式化噪音、调试残留？
- 错误在发生的地方处理了吗？原始错误保留了吗？
- 新路径处理空输入、边界值、超大输入了吗？不能只走正常路径。
- 行为退化时测试会红吗？测试避开实现细节了吗？
- 公开接口、文档、例子跟着行为一起更新了吗？
- 注释写契约，不把改动经过讲一遍吧？
- 密钥、凭据、机器相关路径都没有吧？
- 改动留下死代码、没用到的导出、过时的引用了吗？
- 评审人撤掉其中一小块，会有测试或检查失败吗？没有，这块就没验证过。

## 决策记录

决策记录保存在改动合并后仍然有效的决策：结构选择、值得记住的已否决方案、兼容性承诺、未来维护者可能重新讨论的权衡。记录放在 `.agents/notes/`，状态编码在文件夹里，读者不打开文件就能区分提案和已实施的决策。

[记录格式](../.agents/notes/README.md)规定：固定头部、按生命周期组织的正文骨架、必写的 `## Alternatives considered` 一节，以及作废和删除的规则。决策和记录在同一次改动中提交；已有记录持有该决策时，更新那份记录，不要新建。

决策记录不代替代码和文档；当前行为以代码和文档为准。
