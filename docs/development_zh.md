# 开发指南

*[English](development.md)*

这份文档讲两件事：在本仓库怎么完成一次改动，怎么判断改动做完了。指令标准见 [AGENTS.md](AGENTS.md)；agent 每次会话都要读的常驻规则，在[根目录 AGENTS.md](../AGENTS.md)。

## 改动纪律

1. **先读懂，再动手。** 读目标文件、它的测试，再读一份同模式的邻近例子。改动跨过包或模块的边界，边界的定义也要读。
2. **计划落在纸面上。** 三条：改什么、可能弄坏什么、怎么验证。计划凑出第四条，这次改动就大到一次做不完。
3. **改动面越小越好。** 能改现有函数，就不平行加一个；能扩展现有配置对象，就不新增配置文件；能加一条测试，就不重写整套。
4. **边改边删。** 改动让代码、配置或文档过时了，在同一次改动里删掉，并修好指向它的引用。留着「以后再说」，是把能跑的系统变成负债。
5. **没有理由就不加依赖。** 理由要看它省下的代码和维护量，不能只图一时方便。
6. **提交要读得懂。** 一次提交一个逻辑改动，提交信息写清为什么。格式化噪音不和行为改动混在一起。

## 失败与错误处理

- **在入口校验。** 数据从用户、文件、网络调用、进程或模型进来，就在入口挡。类型化的同进程边界内，相信类型，不做防御性重复校验。
- **结果不明就停下汇报。** 写失败、超时、批量做了一半：说清已知什么、不知道什么、要用户定什么。绝不破坏性重试，绝不假装成功。
- **保留病因。** 包一层错误加上下文，原消息和堆栈都留着。日志只在处理错误的地方打一次，不要每层都打。
- **吞掉的错误要点名。** 空的 `catch` 里写条注释，说清预期哪个错、为什么继续往下走安全。

## 验证阶梯

跑能抓住你错处的、最便宜的那项检查；改动撑大了范围，再放宽。

1. **针对性测试**，对准改动的函数或文件。
2. **包或模块的整套测试**，改了共享辅助函数或公开行为时跑。
3. **Lint 和类型检查**，改了签名、配置，或任何编译器看得见的东西时跑。
4. **全套测试**，只有全仓库范围的改动、排查 CI，或用户要求时才跑。穷尽覆盖归 CI 管；本地把已经通过的全套再跑一遍，费时间，不添证据。
5. **构建产物或手动跑一次**，改动影响用户真正会执行的东西时跑。

跑了什么、返回什么，原样报。「应该能过」不算结果。某项检查在当前环境跑不了，说清是哪项、为什么，不要悄悄跳过。

## 审查清单

交出去之前，先读自己的 diff，逐条回答。

- 这次改动只做一件事吗？描述说清做了什么、为什么了吗？
- 每个改动的文件都有理由吗？有没有格式化噪音、调试残留？
- 错误在发生的地方处理了吗？病因留住了吗？
- 新路径处理空输入、边界值、超大输入了吗？不能只走正常路径。
- 行为退化时测试会红吗？测试避开实现细节了吗？
- 公开接口、文档、例子跟着行为一起更新了吗？
- 注释写契约，不把改动经过讲一遍吧？
- 密钥、凭据、机器相关路径都没有吧？
- 改动留下死代码、没用到的导出、过时的引用了吗？
- 评审人撤掉其中一小块，会有测试或检查失败吗？没有，这块就没验证过。

## 决策记录

决策记录收留活过 diff 的决策：结构选择、值得记住的否掉方案、兼容承诺、将来的维护者还会翻出来争的权衡。记录放在 `.agents/notes/`，状态编码在文件夹里，读者不打开文件就能分清提案和已落地的现实。

[记录格式](../.agents/notes/README.md)规定：固定头部、按生命周期走的正文骨架、必写的 `## Alternatives considered` 一节，以及作废和删除的规则。决策和记录写在同一次改动里；已经持有该决策的记录，更新它，别另开一份。

决策记录不是变更日志，也不是教程。读者要了解当前行为，看代码和文档。
