# AGENTS.md —— 仓库指令与文档

*[English](AGENTS.md)*

本文件规定本仓库的指令和文档怎么组织：什么内容归哪一层、各层怎么加载、规则怎么写、一份文件什么时候算超出了预算。操作步骤——改动怎么做、怎么验证——见 [development.md](development.md)。

这次拆分的原因记在[第一份决策记录](../.agents/notes/implemented/2026-11-02-layered-agent-instructions.md)里。

## 层级模型

一个事实只有一个归属。别处一律链接过去。系统不塌缩成一份没人读得完的文件，靠的就是这条。

| 层级 | 放什么 | 不放什么 |
| --- | --- | --- |
| 根目录 `AGENTS.md` | 常驻规则：agent 每次会话都要带在上下文里的规则，每条一到三行，各自链接到它的归属 | 故事、完整例子、一步步的操作步骤、任何从链接过来的文档里转抄的话 |
| 子目录 `AGENTS.md` | 只管这个目录的规则，也只有这些 | 根文件已经写过的规则 |
| `docs/` | 操作步骤、架构图、像本文件这样的标准 | 决策理由，抄一遍就烂 |
| `.agents/skills/` | 只在一种情形下用得上的操作步骤；描述匹配上任务时才加载 | 每次会话都需要的规则、产品契约 |
| `.agents/notes/` | 决策为什么这么做、否掉了什么、代价是什么；状态编码在文件夹里 | 当前行为，归代码和文档 |
| 代码注释和文档注释 | 局部契约：前置条件、保证、失败模式、不显然的归属 | 复述代码、把实现过程讲一遍、留着评审历史 |
| `README.md` | 项目是什么、怎么跑、从哪入手 | 给 agent 的规则 |

预算按词数计：

| 文件 | 上限 |
| --- | --- |
| 根目录 `AGENTS.md` | 1,200 |
| 子目录 `AGENTS.md` | 400 |
| `docs/` 下每份文档 | 1,200 |

预算是护栏，不是目标。清单文件 [`scripts/doc-budgets.json`](../scripts/doc-budgets.json) 说了算，覆盖上面这些兜底值；`npm run check` 读它、数词、解析每一条站内链接和标题锚点，还要求行尾正好一个换行。文件超了，先把内容挪到它该在的归属，其次精简，最后才提上限——提上限的那次改动得说清这些词为什么非留不可。一份文件长期贴着上限，它就不再是摘要了。决策记录不计预算：一份文件一条决策，记录只随它承载的推理增长。

根文件的试金石：agent 漏掉这条规则，会不会很可能做错事？答案是「只在动 X 的时候」，这条规则就该进 X 的子目录文件，不进根文件。

## 指令怎么加载

多数 agent 框架会自动加载指令文件，加载机制解释了上面的规则。

- **从宽到窄。** 链条从仓库根目录一路连到 agent 正在干活的目录。更近的文件后加载，冲突时赢。
- **去重。** `CLAUDE.md` 和 `AGENTS.md` 内容重复时，只渲染一份。
- **有预算。** 每条链条按字节计预算。超了，先丢更宽的文件，最后才截断最具体的那份，因为具体的文件通常跟当前任务更相关。
- **加载一次，访问时刷新。** 碰到的目录在下一次请求时把它的文件拉进来；改过、删掉的文件会对齐。

两个实际后果：

1. 别为了让规则更显眼就跨层重复。重复让同一份预算付两遍钱，还造出两个会漂移的事实。
2. 规则能放多深就放多深，同时让每个需要它的人都读得到。部署脚本的规则，放在部署脚本旁边。

## 规则怎么写

- **命令式，一个分句，粗体打头。** 先 `**就近大声失败。**`，再跟一句话。粗体打头是 agent 扫读时找到规则的方式，后面全是细节。
- **触发条件和动作都点名。** 「改完分词器跑一遍解析器测试」胜过「让测试保持绿」。规则对不上 agent 工作里的某个时刻，就白写了。
- **附上理由或链接。** 看懂的规则 agent 才照着做，看不懂的会用过头。长篇大论的理由放进 [`.agents/notes/`](../.agents/notes/README.md) 下的决策记录，链过去。
- **写当前行为。** 历史归 git 和决策记录。「我们不用 X 了」「将来会迁到 Y」都不是规则；「新代码用 Y」才是。
- **别转抄清单。** 包列表、选项表、测试目录归源文件或生成器。手抄的清单是一句等着成假的话。
- **慎用强调。** 处处加粗、大写、标「critical」，等于没有强调。强调标出的是改变行为的那个分句。
- **写给能干但新来的读者。** 不用比喻，不用圈内传承的简称，不提某次会议、某次聊天。

一条规则只有改变了 agent 本来会做错的决定，才挣得到位置。复述合格工程师本就遵守的做法的规则，删掉；它们稀释了要紧的那些。

## 双语文档

- **英文是源，中文是译文。** `docs/usage.md` 和 `docs/usage_zh.md` 是同一份文档的两个文件；主名一致，只差后缀。
- **开头几行双向链接。** 从哪个文件进来的读者，点一次就能到另一个；缺链接，门禁报错。
- **译意，不译句式。** 留着英文语序的中文孪生文件，读起来像机翻。用中文把句子重写一遍，事实、数字、命令一个字都不许动。
- **英文改动后要重译对应段落。** 英文那份如果后改过，`npm run check` 会把这个文件判为过期；段落要按新意重写，不能留着旧稿。真要分批处理，先把文件记进 `pendingTranslations`，处理完再删掉。
- **移动、改名、删除，两半在同一次提交里做。** 一对文件漂开，比只用一种语言更糟：读者会信错的那份。
- **两半守同一个预算。** 中文比英文长，它的上限是英文预算乘 `scripts/doc-budgets.json` 里的 `zhMultiplier`；计量单位是一个 CJK 字符算一，一个拉丁词算一。
- **只豁免生成的文件。** `excludePairs` 里列的文件可以只说一种语言；手写的都要配对。

## 维护这些文件

- **每季度复盘一次，出事之后也复盘。** agent 做错事，就补上缺失的规则，或删掉误导它的规则。
- **往下长。** 文件逼近预算时，把一段挪进子目录文件或它所属的操作步骤文档，原地留一行。
- **能删就删。** 两年攒下来的规则，攒出一份没人读的文件。规则对不上现实了，改它或删它；过时的规则在主动教错东西。
- **链接和新旧都用机器查。** `npm run check` 解析每一条站内链接和标题锚点，还会报出英文改过、中文没跟上的那双文件。断链是悄无声息的失败，出的正是 agent 最信任的地方。
- **没有执行者的规则只是建议。** 违反它也不会让某项检查失败，就在规则里说明，或者承认它靠评审兜底。
- **违规先当文档 bug 查。** agent 反复无视一条规则，多半是规则含糊、埋得太深，或跟别处的规则打架。先改写法，别急着怪 agent。

## 废话清单

提交任何指令文件之前，拿它过一遍：

- 重复的规则：搜一句特别的话；留一个归属，其余链接过去。
- 历史待错了地方：写当前事实，链接记录。
- 正文里的状态标注（"implemented"、"planned"）：状态由代码和目录树携带。
- 手抄的清单：链接源文件。
- 推理过程：留结论，删掉得出它的路。
- 大段文字：拆开，或把细节下放给它该在的归属。
- 强调通胀：处处加粗等于处处不加粗。
