# AGENTS.md —— 仓库指令与文档

*[English](AGENTS.md)*

本文件规定本仓库指令和文档的组织方式：什么内容归哪一层、各层如何加载、规则如何写、文件何时算超出预算。操作流程——如何完成改动并验证——见 [development.md](development.md)。

这次拆分的原因记在[第一份决策记录](../.agents/notes/implemented/2026-11-02-layered-agent-instructions.md)里。

## 层级模型

每个事实只有一个归属，其他地方一律链接过去。没有这条规则，各份文件会逐渐膨胀成一份读不完的文档。

| 层级 | 放什么 | 不放什么 |
| --- | --- | --- |
| 根目录 `AGENTS.md` | 常驻规则：agent 每次会话都需要放在上下文里的规则，每条一到三行，各自链接到它的归属 | 背景故事、完整示例、分步操作流程、任何从链接文档转抄的内容 |
| 子目录 `AGENTS.md` | 仅适用于该目录的规则 | 根文件已经写过的规则 |
| `docs/` | 操作流程、架构说明、本文件这样的标准 | 决策理由；转抄的副本很快会过时 |
| `.agents/skills/` | 只在特定情形下使用的操作流程；描述匹配任务时才加载 | 每次会话都需要的规则、产品契约 |
| `.agents/notes/` | 决策的理由、否决的方案、代价；状态编码在文件夹里 | 当前行为，由代码和文档描述 |
| 代码注释和文档注释 | 局部契约：前置条件、保证、失败模式、不显然的归属 | 复述代码、叙述实现过程、保留评审历史 |
| `README.md` | 项目是什么、如何运行、从哪里入手 | 给 agent 的规则 |

预算按词数计：

| 文件 | 上限 |
| --- | --- |
| 根目录 `AGENTS.md` | 1,200 |
| 子目录 `AGENTS.md` | 400 |
| `docs/` 下每份文档 | 1,200 |

预算用于限制增长，不需要用满。清单文件 [`scripts/doc-budgets.json`](../scripts/doc-budgets.json) 是最终依据，覆盖上面的默认值；`npm run check` 读取清单：词数预算、双语配对、链接与标题锚点、固定的决策记录头部、末尾恰好一个换行，以及不许链接跑出仓库。文件超限时，先把内容移到它该在的归属，其次精简，最后才提高上限；提高上限的改动必须说明这些词为什么必须保留。一份长期贴着上限的文件已经不再是摘要。决策记录不计预算：一份文件一条决策，只有在决策需要更多解释时才增加篇幅。

根文件的判断标准：agent 漏掉这条规则，是否很可能做错事？如果答案是「只在修改 X 的时候」，这条规则就该放进 X 的子目录文件，而不是根文件。

## 指令如何加载

多数 agent 框架会自动加载指令文件，加载机制解释了上面的规则。

- **从宽到窄。** 加载链从仓库根目录一直到 agent 正在工作的目录。更近的文件后加载，冲突时以它为准。
- **去重。** `CLAUDE.md` 与 `AGENTS.md` 内容重复时，只渲染一份。
- **有预算。** 每条链有字节预算。超出时，先丢弃更宽的文件，最后才截断最具体的文件，因为具体的文件通常与当前任务更相关。
- **加载一次，访问时刷新。** 访问过的目录在下一次请求时加载其文件；修改或删除的文件会同步更新。

两个实际后果：

1. 不要让规则跨层重复来换取显眼。重复会占用两份预算，还会产生两份终将不一致的副本。
2. 规则能放多深就放多深，同时保证每个需要它的人都能读到。部署脚本的规则，放在部署脚本旁边。

## 规则怎么写

- **命令式，一个分句，粗体开头。** 先写 `**就近大声失败。**`，再跟一句话。粗体开头方便 agent 扫读时定位规则，后面是细节。
- **写明触发条件和动作。** 「改完分词器后运行解析器测试」好过「保持测试通过」。无法对应到 agent 工作中某个时刻的规则会被忽略。
- **附上理由或链接。** agent 会遵守它理解的规则，过度执行它不理解的规则。长篇理由放进 [`.agents/notes/`](../.agents/notes/README.md) 下的决策记录并链接过来。
- **写当前行为。** 历史归 git 和决策记录。「我们不再使用 X」「将来会迁移到 Y」都不是规则；「新代码使用 Y」才是。
- **不要转抄清单。** 包列表、选项表、测试目录归源文件或生成器。手抄的清单会过时，然后误导读者。
- **慎用强调。** 处处加粗、大写、标「critical」，等于没有强调。强调只标改变行为的那个分句。
- **写给有能力但新来的读者。** 不用比喻，不用圈内简称，不提某次会议或某次聊天。

只保留能改变 agent 本来会做错的决定的规则。复述合格工程师本就遵守的做法的规则要删掉，它们会稀释重要的规则。

## 双语文档

- **英文是源稿，中文是译文。** `docs/usage.md` 和 `docs/usage_zh.md` 是同一份文档的两个文件；主名一致，只差后缀。
- **开头几行双向链接。** 读者从哪个文件进入，点一次就能到达另一个；缺链接时检查会报错。
- **译意，不译句式。** 保留英文语序的中文译文读起来像机器翻译。用中文重写句子，事实、数字、命令保持精确。
- **英文改动后要重译对应段落。** 英文后改动的文件无法通过 `npm run check`；按新的内容重译受影响段落，不要保留旧稿。需要分批处理时，先把文件列入 `pendingTranslations`，完成后再移除。
- **移动、改名、删除，两半在同一次提交里完成。** 两份内容不一致比只用一种语言更糟，因为读者可能相信过时的那一半。
- **两半遵守同一个预算。** 中文比英文长，上限是英文预算乘 `scripts/doc-budgets.json` 里的 `zhMultiplier`；计量单位是一个 CJK 字符算一，一个拉丁词算一。
- **只豁免生成的文件。** `excludePairs` 里列的文件可以只保留一种语言；手写的都要配对。

## 维护这些文件

- **每季度复盘一次，出问题后也复盘。** agent 做错事，就补上缺失的规则，或删掉误导它的规则。
- **向下扩展。** 文件逼近预算时，把一段移到子目录文件或它所属的操作文档，原处留一行链接。
- **优先删除。** 两年积累下来的规则会让文件没人读。规则与现实不符时，修改或删除它；过时的规则会误导每个信任它的读者。
- **链接和时效用脚本检查。** `npm run check` 解析每条站内链接和标题锚点，并报告英文已改、中文未跟上的文件。指令文件里的断链会让 agent 找到错误的位置，或什么都找不到。
- **没有执行者的规则只是建议。** 违反它也不会让任何检查失败，就在规则里说明，或承认它依赖评审。
- **违规先当文档 bug 查。** agent 反复无视一条规则，多半是规则含糊、埋得太深，或与别处的规则矛盾。先改写法，不要急着怪 agent。

## 提交前自查

提交任何指令文件之前，对照这张清单检查：

- 重复的规则：搜一个有特征的短语；保留一个归属，其余链接过去。
- 历史放错了位置：写当前事实，链接到记录。
- 正文里的状态标注（"implemented"、"planned"）：状态由代码和目录树表达。
- 手抄的清单：改为链接源文件。
- 推理过程：保留结论，删掉得出结论的过程。
- 大段文字：拆开，或把细节移到它该在的归属。
- 处处强调：每行都加粗等于什么都没标。
